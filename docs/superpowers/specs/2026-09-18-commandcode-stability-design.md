# CommandCode 代理稳定性修复

已根据本机日志和离线复现确认：工具调用未进入 Responses 最终 output，纯工具响应追加空 assistant；历史转换隔断工具调用与结果；流式首事件失败仍返回 200；网络异常丢失 cause，未实际重试；客户端断开未取消上游。

采用定向修复现有 TypeScript 适配器的方案。仅调整超时无法解决协议错误；重写代理风险和范围过大。Go provider 服务不属于本次生成链路。

## 行为约束

- Responses 工具输出在增量事件和最终 output 中具有一致 ID、顺序；没有正文时不追加空消息。历史按 assistant 轮次合并，保留 system/developer 和推理语义。
- namespace 中的 function 工具展开为唯一名称，输入历史和输出恢复命名空间。无法执行的托管工具明确指出字段和能力限制，不能静默丢弃。
- 上游首事件 error/abort 在 HTTP 提交前返回原始错误状态；流中失败以 response.failed 终止，保留状态码。客户端断开取消上游，正常结束清理监听。
- 网络异常记录阶段、attempt、elapsed、原始 message/cause.code，脱敏凭证。最多三次请求，仅在尚未产出任何事件、属于明确瞬时故障时重试；400/401/403 不重试，取消和总超时不重试，已输出流不重放。
- 保持一个总超时预算。重试退避受取消控制，清理连接和监听，保留已有 max_tokens 上限。
- 回归测试必须先失败再修复；增加实际 HTTP 断开测试和模拟上游端到端测试。

## 部署验收

在隔离 worktree 验证测试、类型检查和构建。备份当前 dist，将通过验证的构建部署到主目录，重启 3000 端口的实际 Node 服务。健康、错误响应及真实上游文本/工具多轮测试通过后再提交、合并 main、推送 main 的跟踪远端 github。失败时恢复旧构建。保留 worktree 目录，删除本次临时分支。
